# ATS-IDENTITY-001 身份映射器设计书（文件/标题变化时的 UID 重识别与歧义提示）

- 对象：测试用例的**身份重识别**——文件改名、标题改写、模板改写之后，用例仍是同一个用例
- 目标版本：v0.2.0（S2 / WBS ATS-204）
- 实现：`server/identity.mjs`（映射器，纯函数无 IO）、`server/execution/model.mjs`（运行侧绑定）、`server/discovery/authoritative.mjs`（发现侧锚点）、`server/core.mjs`（目录面）
- 实测脚本：`tools/ats204-probes/`
- 证据：`docs/evidence/ATS-204/`
- 状态口径：本文件描述**已实现且有实测证据**的能力。尚未实现的部分列在 §7。

## 1. 为什么需要身份映射器

用例的 UID 承载着它与外部世界的所有关联：需求关联、旧运行的证据、已归档的
产物。仓库会变——文件会改名，标题会改写，模板会改文案——而 UID 必须跟着
用例走。

三种变化，三种难度：

| 变化 | 现有能力 | 缺口 |
|---|---|---|
| 文件改名 | 已有（注册表按执行体指纹认回） | 已实现，但**运行侧**没有用上这个信号 |
| 标题改写（执行体未变） | 已有（同上） | 同上 |
| 文件改名 **且** 标题改写 | **无** | 运行侧完全认不出这个用例 |
| 模板改文案（动态用例） | **无** | 动态用例没有自己的执行体，标题是它唯一的身份 |
| 项目矩阵 | **无** | 一个用例跑两个 project 被算成两个用例 |

「运行侧没有用上这个信号」是关键：**注册表早就记着执行体指纹**，但运行
结果的绑定没有用它。改完名又改了标题的用例，运行结果是 `unbound` 的——
旧证据与用例的关联就断了。

## 2. 三条纪律

映射器做的是「报告里的这个用例是不是注册表里那个用例」的判断。三条纪律
贯穿全部实现：

1. **不唯一的信号绝不决定。** 当有多个候选时，映射器报出候选并且**不绑定**。
   绑错是静默的——报告看起来照样完整；丢链接至少是可见的。
2. **信号按强度排序使用。** 位置弱于执行体：上面插入一个用例，下面所有
   行号都平移。执行体强于标题：标题常改，执行体很少改。
3. **标题在项目内不唯一时，标题不决定任何事。**

## 3. 运行侧的信号阶梯

`server/identity.mjs` 的 `bindReported()` 按下列顺序走，先命中者生效：

| # | 信号 | `uidBasis` | 扛得住什么 |
|---|---|---|---|
| 1 | 显式标注 `@TC-<token>` | `explicit` | 一切 |
| 2 | 文件 + describe 路径 + 标题 | `file-scope-title` | 文件内移动 |
| 3 | 文件 + 行号 + 标题 | `file-line` | 改标题 |
| 4 | 文件 + 标题 | `file-title` | 文件内移动 |
| 5 | **执行体指纹** | `body-key` | **改名 + 改标题** |
| 6 | **别名**（注册表记的旧拼写） | `alias` | 改回去 |
| 7 | 标题单独 | `title` | 换文件 |

### 3.1 位置信号必须与执行体一致

行号**不是身份**（`docs/18-UID-SPEC.md` §7.1 记着这条边界）：同一个文件里
两个同名用例，在上面插入几行之后，其中一个会落到另一个的旧行号上。
按「行号 + 标题」绑定会把它绑到**别人的 UID**，而且看上去没有任何异常。

所以：**执行体算得出来时，位置命中必须与执行体一致**。位置命中但执行体
对不上时，位置不算数（`file-line-body-mismatch`），落到执行体信号上。执行体
算不出来时，位置单独成立——那是仅剩的证据，边界写在 `uidBasis` 里。

**信号 2（`file-scope-title`）走同一条规则。** describe 路径是位置，不是
身份：它同样会因用例上下移动而失效，所以它命中时也要与执行体一致。实现上，
信号 2 的执行体检查用的是**同一 scope 内的**指纹唯一性：两个用例共享执行体
但坐在**不同**的 describe 路径下时，它们本来就是两个用例，describe 路径
正是把它们分开的那件事——此时信号 2 不被「执行体共享」挡住。

### 3.2 整次运行才算得清的四件事

映射器一次只被问到一个用例，但有四个信号只能对着**整次运行**判断。

**执行体在本次运行里被共享。** 两个用例共享执行体时，这个指纹认不出其中
任何一个。此时任何**不使用**指纹的信号都不能绑定——否则两个用例会拿到同
一个 UID，那正是本任务要防的静默误关联。位置信号同样不绑定：位置不是身份。

**执行体在本次运行里被共享，但只在同一 describe 路径下共享。** 见 §3.1：
这种共享不挡住信号 2。

**同一个显式 token 在本次运行里出现两次。** token 属于写下它的那个用例，
而且属于**一个**用例。本次运行里两个用例都写了 `@TC-001`，谁也不拥有它。
映射器被逐个问，所以必须被告知本次运行里各 token 出现了几次。

**目录已经判定 token 重复。** 见 §3.4：目录的判定是权威的。

### 3.3 别名：注册表记下的旧拼写

用例移动时，注册表把它的旧拼写记进 `aliases`。旧拼写能认出「这次运行之前
的写法」，因此一份**在移动之前**写下的报告仍然能解析到它说的那个用例。

别名**只在执行体不可得时使用**。执行体算得出来却不匹配，说明那个位置上
是**另一个**用例，别名不得认领它。

### 3.4 显式 token：目录的判定是权威的

token 属于写下它的那个用例，而且属于**一个**用例。两种情况谁都不拥有它：

1. **本次运行里两个用例都带这个 token**——只有作者知道它属于谁；
2. **目录已经判定这个 token 在项目内重复**（`duplicate-explicit-uid`）。

第 2 种是第 1 种的**超集**：一次只跑其中一个文件的运行（`safeRunArgs`
支持单文件），本次运行里那个 token 只有一个携带者，但项目里有两个。目录
已经判定「谁都不拥有它」，运行侧必须与之一致——否则运行侧会把 token 绑给
其中一个用例，两个用例就拿到了同一个 UID。

目录的判定记在注册表条目的 `duplicateExplicit` 字段里，运行侧读它。

**两个目录都要记这个判定。** 权威目录（可信项目，`playwright test --list`）
和静态目录（默认路径，不可信项目）都会判定 token 重复，而运行侧读的是
**注册表**——判定必须落在注册表条目上，运行侧才看得到。静态路径此前把
判定留在候选上、没写进注册表，于是默认路径上的单文件运行会把重复的 token
绑给其中一个用例，与目录的判定相反（实测：`tools/ats204-probes/review-r2/
r2-e2e.mjs` 的 X3）。

判定是关于**项目当下**的陈述：重复被修好之后，判定随之消失，token 重新
可以绑定（实测：同一探针的 X2/X2s）。

## 4. 发现侧的锚点

### 4.1 位置加次序

动态用例（静态扫描器看不见的：循环、helper、fixture）**没有自己的执行体**：
那个位置上的执行体是**模板**的，而模板明天可能多生成一个用例——把模板的
指纹当成用例的指纹，等于把模板和用例混为一谈（`docs/23-AUTHORITATIVE-DISCOVERY.md`
§4.2）。

所以动态用例的身份是**位置**加**次序**：

```
位置 = 文件 + `test(` 调用所在行 + describe 路径
次序 = 该位置上的第几个（组内序号）
```

注册表为每个用例记下这个**锚点**（`anchor`），权威发现按锚点找回用例。

### 4.2 次序是 CLI 的报告次序，不是排序名次

**次序 = CLI 报告这些渲染的次序，也就是模板生成它们的次序。**

目录自己的**显示次序**是按标题排的（`parseListReport` 的 sort），而改文案
会改变一个标题的排序名次。两个次序不是一回事：

- 报告次序：模板写 `for (const n of [2, 1])`，CLI 就先报 `adds 2 items`；
  锚点的次序 0 是它。
- 排序名次：按标题排，`adds 1 items` 在 `adds 2 items` 前面。

如果锚点按排序名次计数，改文案之后每个渲染的名次都可能变，锚点就会指向
**另一个**渲染。因此 `parseListReport` 把 CLI 的报告次序记在用例的
`reportOrder` 上，分组按它排序。

实测：真实 `@playwright/test` 1.64.1 对 `for (const n of [2, 1])` 报告
`adds 2 items` 在前——`tools/ats204-probes/cli-facts.mjs` 的
「the report order is NOT the title-sorted order」一项。

### 4.3 锚点不得覆盖已有的身份

锚点是**最弱的**信号：它说的是「第几个」，是关于**位置**的事实，不是关于
**用例**的事实。它只能补上强信号补不上的空，不能反过来改写。四条规则：

1. **静态扫描器看得见的用例，锚点不决定。** 这样的用例有自己的执行体，
   执行体（和标题）都比次序强。
2. **标题仍然认领着注册表里某个用例的，锚点不决定。** 标题是渲染用例的
   身份，次序只是它的兜底。
3. **组内只有一部分标题变了，锚点不决定。** 删掉一个渲染、加上一个渲染，
   渲染**总数不变**，但新渲染可能坐在被删渲染的次序上——按次序绑定就是把
   新渲染绑到消失那个用例的 UID 上。此时报 `render-partially-changed`
   并且**不绑定**。
4. **站在源码用例位置上的另一个用例，锚点不决定。** 注册表里的**源码条目**
   带执行体指纹（`bodyKey`），而动态用例不带（那个位置上的执行体是模板的）。
   一个标题不同的用例站在源码用例的位置上，它是另一个用例——或者是原来
   那个用例换了执行体，而**换了执行体就是换了身份**（ATS-201 的边界，
   `docs/18-UID-SPEC.md` §3.2）。此时报 `render-source-entry` 并且
   **不绑定**：把旧 UID 给它，就是把旧证据挂到另一个用例上。

这四条规则只写在**一处**：`server/identity.mjs` 的 `reidentifyRendered()`。
生产路径（`server/discovery/authoritative.mjs`）调用的就是它——锚点曾经
在两处各有一份实现，而跑的是没写进文档的那一份。

### 4.4 模板改文案

模板的文案改了，于是**每一个渲染出来的标题都跟着改了**，而标题是动态用例
唯一的身份。锚点是唯一认得出它的东西：

```
模板改文案前：adds 1 item      -> tc_1_d_06b302ca4e456309
模板改文案后：adds 1 item to the cart -> tc_1_d_06b302ca4e456309（basis=position-anchor）
```

实测：`tools/ats204-probes/probe-anchor.mjs`。

### 4.5 模板增减渲染：报位移，不猜

模板多了一个或少了一个渲染，组内次序可能整体位移——**位移后的次序指向的是
另一个渲染**。这时映射器不绑定，而是报 `render-shift-possible`，并带上
位移前后的渲染数。

次序没有位移时锚点才生效。位移报告走的是用例的 `ambiguity` 字段，与其他
所有不确定性同一条通道。

## 5. 项目矩阵：一个用例，不是一个用例一个 project

### 5.1 实测事实

真实的 `@playwright/test` 1.64.1 对**每个 project 各写一行 spec**。同一个
逻辑用例跑两个 project，就是两行 spec、两个 spec id、各一个 `test`：

```
file=facts.spec.ts line=4 title="plain case" id=...-22a33c5b2ba004a151fd  project=alpha
file=facts.spec.ts line=4 title="plain case" id=...-13260e8b00170836d823 project=beta
```

实测脚本：`tools/ats204-probes/cli-facts.mjs`（真实 CLI，真实安装）。

### 5.2 修正

产品的报告解析器给**每个** spec 加了序号，于是这两行成了两个用例：
「在 project b 里失败的用例」被报成「一个通过的用例 + 一个失败的用例」，
计数也是 `total: 2`。

序号现在**只给没有行号的 spec**——那才是报告真的分不开的用例。带行号的
spec 按位置区分，同一位置的两行就是同一个逻辑用例在两个 project 里的两次
执行。

### 5.3 两条报告形状现在给同一个答案

| 报告形状 | 修正前 | 修正后 |
|---|---|---|
| 真实 CLI（每个 project 一行） | `total: 2`、一个 passed 一个 failed | `total: 1`、`failed: 1` |
| 产品自己的测试（一个 spec，多个 test） | `total: 1`、`failed: 1` | `total: 1`、`failed: 1` |

两种形状给同一个答案——这是「与 CLI 一致」的真正含义。

## 6. API 面

| 接口 | 变化 |
|---|---|
| `GET /api/projects/:id/tests` | 权威索引的用例新增 `anchor`（位置 + 次序 + 组的大小） |
| `GET /api/projects/:id/tests` | `warning` 增加模板渲染数变化的提示（位移的渲染数） |
| `GET /api/runs/:id` | 每个 attempt 新增 `uidAmbiguity`（映射器无法判定时的原因与候选） |

`uidAmbiguity` 是**绑定失败的原因**，不是猜测。映射器绑不出来时，attempt
保持未绑定，并说明为什么——一个什么都不说的未绑定 attempt，与「用例根本不在
目录里」分不开。

## 7. 已知边界

以下能力**本设计未实现**，不得据本文件宣称已具备：

| 边界 | 归属 |
|---|---|
| 跨机器的用例身份（Project UID 依赖绝对路径） | 见 `docs/18-UID-SPEC.md` §3.1 |
| `test.each` 的标题模板与渲染标题的对应关系 | 真实 Playwright 1.64.1 **没有** `test.each`（实测：`tools/ats204-probes/cli-facts.mjs`），参数化在 Playwright 里是循环；标题模板的对应关系属其它引擎 |
| 非 Playwright 引擎的权威发现（WDIO） | ATS-302 |
| 同一逻辑用例的**跨 project**身份（当前一个用例携带每个 project 的 spec id，但 UID 按逻辑用例唯一） | 本设计已实现矩阵侧的计数与绑定；spec id 到具体 project 的映射仍由 `specIds` 承担 |
| 沙箱化执行（`--list` 在宿主上执行仓库代码） | ATS-415 |
| 标题的**语义**相似（改标题不只是改字，改的是意思） | 不可能自动判定；`@TC-xxx` 是唯一的确定手段 |
| **`body-key` 的范围跨文件** | 第 5 步（执行体指纹）的查找范围是**整个项目**，而唯一性只在**本次运行内**计算。于是：一个新文件里复制来的同一执行体，在注册表陈旧时会绑到**旧**用例上。要固定身份就用显式标注 `@TC-xxx`；这条边界由本设计记录，不宣称已解决 |
| **同一 describe 路径下共享执行体** | 两个用例共享执行体且坐在**同一** describe 路径下时，指纹认不出其中任何一个，任何不使用指纹的信号都不绑定（§3.2）。跨 describe 的共享不挡住信号 2（§3.1） |
| **循环数据整体替换与模板改文案不可区分** | 锚点认的是「第几个渲染」，不是「哪个渲染」。把循环的数据**全部**换掉（`alice,bob` → `carol,dave`），渲染的**个数**不变，锚点分不出这是「改文案」还是「换了数据」——于是新渲染按次序继承了旧渲染的 UID。锚点能分辨的是**部分**改动（组内还有旧标题在），那种情况报 `render-partially-changed` 并不绑定（§4.3 规则 3）。整体替换要固定身份就用显式标注 `@TC-xxx` |
| **源码用例原位改成循环，锚点不再沿用旧 UID** | 一个源码用例（注册表条目带执行体指纹）被原位换成一个只渲染一次的循环时，新用例**不继承**旧 UID，报 `render-source-entry`（§4.3 规则 4）。这与下面的「改执行体就换身份」是同一条边界 |

**改标题就改身份的情形**：用例的执行体被改了，此时指纹变了，标题也变了，
用例就换了身份。这条边界是 ATS-201 定下的（`docs/18-UID-SPEC.md` §3.2），
本设计不改变它——要固定身份就用显式标注。

**「本设计不改变它」指的是这条边界本身，不是说任何情况下都换身份。** 下列
两种情形本设计**保住**了旧 UID，因为它们都没有改执行体：

| 情形 | 旧 UID | 依据 |
|---|---|---|
| 文件改名，标题不变 | 保住 | 执行体指纹不变（§3 步骤 5） |
| 模板改文案（动态用例） | 保住 | 位置与次序不变（§4.1、§4.4） |
| 源码用例原位换成动态循环 | **不保住**，换新 UID | 执行体被改了（§4.3 规则 4、§7 表） |
| 循环数据整体替换 | 保住（按次序） | 与「改文案」不可区分（§7 表） |

## 9. 与既有设计的关系

- `docs/18-UID-SPEC.md` §3.2 的**派生规则**没有变。本设计改变的是**绑定**
  （运行侧）与**动态用例的身份**（发现侧），不是 UID 的派生方式。
- `docs/23-AUTHORITATIVE-DISCOVERY.md` §4 的**身份阶梯**没有变。本设计在
  阶梯之前加了一步「按锚点找回」，因为一个改写了标题的渲染用例，其标题键
  已经是新的了，认领它的只能是锚点。
- `docs/24-EXECUTION-MODEL.md` 的**执行模型**没有变。本设计改的是报告解析
  里「spec 的序号」这一步：序号只给没有行号的 spec。
