- 状态标记沿用仓库约定：`IMPLEMENTED` ＝ 代码能力存在；`DESIGNED` ＝ 仅设计。**本文件不得把设计中的能力称为已实现。**

## 1. 验收标准与本文件的对应

WBS 的完成定义是一句话：

> **从失败用例 2 次点击内找到 Trace；显示附件哈希与时间**

这句话有三段，**三段都是关于诚实的要求，而不是关于排版的要求**：

| 片段 | 要求 | 本文件的落点 |
|---|---|---|
| 从失败用例 | 读者是**从失败用例出发**的，Trace 必须挂在用例上 | §3 用例→附件的映射 |
| 2 次点击内 | 点击次数是**数出来的**，不是写死的文案 | §5 点击预算 |
| 找到 Trace | 找不到就**说找不到**，绝不臆造一条路径 | §3.3 定位失败如何报告 |
| 显示附件哈希与时间 | 哈希与时间必须是**归档时的事实** | §4 归档摘要与文件时间 |

「2 次点击」在本任务里不是一句口号：模块导出 `clickPath`（点击路径），点击预算 `TRACE_CLICK_BUDGET = 2` 由模块返回并显示在界面上，系统测试在**真实浏览器里数真实的点击**（§6）。

## 2. 实现放在哪里：一份实现，两个界面

本仓库有两个界面：Next.js 工作台（`apps/studio/app/page.tsx`）与零依赖便携 UI（`apps/studio/public/fallback.html`）。两者都要显示证据。

Bridge 会把 `apps/studio/out` 与 `apps/studio/public` 当作静态根目录（`server/index.mjs` → `staticFile()`），因此放在 `public/` 下的模块可以被便携 UI 以稳定 URL 取到。把实现放在那里，就只有**一份**「这个用例的 Trace 在哪里」的实现，两个界面不会各说各话——这正是 ATS-216 的质量概览模块已经用过的做法。

模块分成三个文件，**依赖方向严格单向**：

```
evidence-workbench-vocabulary.mjs   词汇：附件种类、优先级、标签（无 import）
              |
              v
evidence-workbench-index.mjs        定位逻辑：用例→附件、用例→Trace
              |
              v
evidence-workbench.mjs              公开接口：视图、点击路径、执行前后对照
```

拆成三个文件的原因是**依赖方向**：词汇被定位逻辑与公开接口同时需要，如果词汇放在公开接口里，定位逻辑就得反向 import 公开接口，形成循环。ES 模块能处理函数声明的循环，但那是脆弱的依赖；单向链没有这个问题。

三个模块都是**纯 ECMAScript Module + JSDoc 类型**，因此可以同时被 Next 应用（TypeScript 读 JSDoc）、Node 的测试运行器（`node --test`）与便携 UI（浏览器 ES module）加载，不需要各自的构建步骤。

## 3. 用例 → Trace：映射是怎么做的

### 3.1 难处在哪

失败的用例留下了一个 trace 归档，但读者是从**用例**出发的，不是从文件出发的。引擎把 trace 写进一个**由用例标题派生**的目录里（实测：`<output>/<文件干名>-<净化后的完整标题>/trace.zip`），而 JSON 报告用**绝对路径**指明每个附件属于哪个结果。

绝对路径读完就没用了：数据目录会搬家、工程会搬家、机器会换。能活下来的是**相对于 run 目录的路径**，而让它有意义的是**摘要**：同样的字节换个名字仍是同一份证据（实测：HTML 报告把 trace 又嵌了一份成 `html/data/*.zip`，SHA-256 与 per-case 的 `trace.zip` **逐字节相同**）。

### 3.2 定位分两步，每一步都可失败

**第一步（权威）：引擎自己的记录。**

引擎在 `report.json` 里为每个 result 写明它产生的每个附件——`{name, contentType, path}`。那份报告就是「哪个附件属于哪个用例」的**唯一权威链接**：trace 的位置无法可靠推导（引擎的命名规则依赖 testDir、describe 路径、项目 id 与重试序号，见 §3.4）。

因此桥接在收集结果时把附件路径**规整为 run 目录下的相对路径**（`relativizeAttachments`）：绝对路径指向跑测试的那台机器，对归档的读者没有意义，而相对路径正是附件下载端点接受的形式。**越出 run 目录的路径被丢弃并计数报告**（`attachmentsOutsideRun`）——这样的路径本来就不是这次运行的证据（下载端点会以 `PATH_OUTSIDE_RUN` 拒绝它），留着就是一条打不开的链接。

**第二步（兜底）：按引擎的命名规则推导。**

报告不可用时（运行被中断、报告无法解析），工作台按引擎的命名规则推导目录名。推导**只有在推导出的路径确实是本次归档的证据之一时**才被接受：标题碰巧与某个不相关的文件同名时，推导不出东西。

### 3.3 定位不到就报告定位不到

这是本任务最重要的一条约束：**臆造出来的 Trace 路径比没有路径更坏**。

一个没有 Trace 的用例，模块返回 `located: false` 与**具体的原因**：

| 原因 | 含义 |
|---|---|
| 该用例没有留下任何附件 | 引擎没有为它写任何文件 |
| 该用例的附件里没有 Trace | 有附件，但其中没有 trace 归档 |
| 该用例的 Trace 不在本次归档的证据清单中（可能已被保留期清理） | 引擎写了，但清单不列它（ATS-209 的保留期清理器删掉了证据文件） |

第三种情况值得单独说：引擎确实写了 trace，但 ATS-209 的保留期策略把它清掉了。这时**不能**把它当成这次运行的证据展示——那是一个归档无法背书的断言。附件仍然列在界面上，但**没有摘要**，并附上原因。

### 3.4 推导规则的实测依据

规则是从引擎源码里读出来的（`playwright/lib/worker/workerProcessEntry.js`）：

```
<测试文件相对 testDir 的路径，去掉 .spec/.test 后缀，分隔符换成 ->
  "-" + 净化过的完整标题（describe 路径 + 用例标题，用空格连接）>
```

净化规则（`sanitizeForFilePath`）：`[A-Za-z0-9]` 之外的连续字符换成单个 `-`，保留最后一个点（它是扩展名的点）。

**推导只在短标题、单项目、未重试时精确**：超长标题会被截断并在中间插入摘要，项目 id 与重试序号会被追加。因此推导**只是兜底**，并且始终要过「这个文件存在吗」的检查；推导不出东西时报「定位不到」，而不是猜。

实测对照：标题 `导航入口正常 @REQ-002` 的推导结果是 `home-导航入口正常-REQ-002`，与真实运行写出的目录名**逐字相同**。

## 4. 附件哈希与时间：归档时的事实

### 4.1 哈希是归档时的摘要，不是现在重算的

工作台显示的 SHA-256 是 **ATS-209 的清单在归档时记录的摘要**，不是读文件现算的。理由是：**这两个是不同的断言**。

一个归档后被改动的文件，现算的摘要会跟着变——显示它等于说「这份证据现在是这样」，而清单里的摘要说的是「这份证据**当时**是这样」。篡改检测（ATS-209 的 `verifyEvidence`）正是要指出这两者的差异。工作台因此显示**归档时的摘要**，并把 ATS-209 的校验结果一并带上来：

| 字段 | 含义 |
|---|---|
| `verified` | 归档是否仍与清单相符（ATS-209 的篡改判定） |
| `ok` | 清单**是否读得出**（读不出 ≠ 被篡改：没有清单与清单里什么都没有是两件事） |
| `missing[]` / `changed[]` | 归档后被删除 / 被改动的文件 |

实测（§6 的 ST-11）：把 trace 改掉之后，校验报出 `changed`（给出应有与实际两个摘要），而工作台**仍然显示归档时的摘要**——两者是不同的断言，谁都不能冒充谁。

### 4.2 时间是文件自己的修改时间

清单不记录时间，界面显示的是**文件在磁盘上的修改时间**（`stat().mtime`）。

这里有一个刻意的选择：**没有**在清单里补一个时间字段。清单里的时间会被读成「归档时刻」，而读者问的是「这个文件是什么时候的」。两者不是同一件事，而清单已经由 ATS-209 定过格式（`version: 2`），往里塞一个未经约定的字段会让清单的语义漂移。

### 4.3 引擎版本随运行走

Trace Viewer 是**引擎附带的独立程序**（`npx playwright show-trace`），它的版本必须与写出该 trace 的引擎一致——这正是本任务 WBS 里登记的风险「Trace Viewer 版本兼容」。

因此适配器**探测到的已安装 CLI 版本**随运行记录一起保存（`run.engineVersion`），工作台把它显示出来：读者打开 trace 之前，就知道自己需要哪个版本的 viewer。版本是**探测来的**，不是猜的。

**本工作台不代为打开 trace。** 它负责定位、校验与说明；打开与否、版本是否匹配，由读者用自己装的 viewer 决定。

## 5. 点击预算是数出来的

`clickPath({located, reason})` 返回**数据**而不是文案：

```js
{
  steps: [
    { action: 'select-case', label: '点击失败用例' },
    { action: 'open-trace',  label: '点击该用例的 Trace' },
  ],
  clicks: 2,
  budget: 2,          // TRACE_CLICK_BUDGET
  withinBudget: true,
}
```

定位不到时，`withinBudget` 是**假**——一条打不开的路径不算「2 次点击可达」。

这个预算是**布局上的事实**，不是断言：失败用例列表在证据工作台的**左栏**，选中用例的 Trace 按钮在**同一屏的主区**，中间不需要任何导航。系统测试在真实浏览器里点两次并断言下载真的发生（§6 的 ST-9）。

**点击次数由探针数出来，不由探针写死。** 探针在页面里挂一个捕获阶段的 `click` 监听器，把**真实发生**的每一次点击记下来，然后与验收标准里的 2 比。预算常数写在探针里（`TRACE_CLICK_BUDGET_CRITERION`），**不从被测模块读**——否则一个把自己预算抬大的模块就能让探针满意。模块自己报的预算另有一条检查（ST-4），两条断言各说各的事。

这条检查有**负控**：让流程真的需要三次点击（多一次落在活动元素上的点击），计数就读出 3，ST-9 转红。恒真的检查抓不住这种回归。

## 6. 执行前后对照（模块与接口基础）

`compareRuns(before, after)` 按**用例身份**配对两次运行。身份取执行模型那四个事实（文件 + describe 路径 + 标题 + 行号，与 ATS-208/ATS-204 一致），因此同一文件里同名的两个用例是两个用例。

每一行给出：前后状态、前后耗时、前后 attempt 数、前后各自的 Trace，以及一个**明确的结论**：

| 结论 | 含义 |
|---|---|
| `fixed` | 之前失败，现在通过 |
| `broken` | 之前通过，现在失败 |
| `same` | 状态没变 |
| `changed` | 状态变了，但不是上面两种 |
| `unknown` | 有一侧没有状态——**不可结论** |

两个关键设计：

- **两侧没有状态时，结论是 `unknown` 而不是 `same`。** 把「不知道」折进「一样」是凭空造出一个结论。
- **两次运行来自不同 commit 时，`comparable` 为假。** 代码变更导致的状态变化，与不稳定用例导致的状态变化不是一回事。这个事实被**报出**，而不是被抹平。

**当前的边界**：跨运行的并排视图**尚未**在界面上提供（模块与接口已具备，属 P1）。本任务交付的是「执行前后对照」的**模块能力与接口基础**，界面目前提供的是单次运行的证据视图。这一点在 WBS 备注与 §9 里都写明了，不把未实现的能力称为已实现。

## 7. 接口面

`GET /api/runs/:id/workbench` —— **只读**，交出**事实**：

```jsonc
{
  "run":     { "id", "uid", "status", "gitCommit", "runner",
               "startedAt", "finishedAt", "engineVersion" },
  "artifacts": [ { "file", "size", "sha256", "modifiedAt" } ],
  "cases":     [ { "title", "file", "line", "status", "duration", "error",
                   "attemptsCount", "scope", "caseKey",
                   "attachments": [ { "name", "contentType", "file" } ] } ],
  "verification": { "verified", "ok", "checked", "missing", "changed", "reason" }
}
```

**视图由共享模块计算，服务端不实现第二份。** 两份「这个用例的 Trace 在哪里」的实现就是两个答案，而它们会漂移——这正是这个模块存在的理由。

### 8.5 用例在册的地方是生成器，不是生成物

`docs/09-ST-TEST-DESIGN.md` 是**生成物**（`tools/generate_test_docs.py`）。本任务的 ST-034..038 一度只写在那份生成物里：下一次重跑生成器，它们就被覆盖掉，而 `tools/test_generate_test_docs.py`（断言提交态与生成器一致）随即报「stale」。

因此这五条用例现在**在生成器里**（`tools/generate_test_docs.py` 的 `ST+=` 块），生成物是它的输出而不是它的来源；`docs/10-RTM.md` 里 FR-014/FR-015 的用例列也因此从 `ST-011` 变成含 ST-034/035/036/037/038——追踪关系由生成器算出，不再靠手工维护。

同一处缺陷也落在 **ATS-203** 的 6 条 ST 与 9 条 IT 上（它们同样只写在生成物里）。这 15 条也一并进了生成器：**用例在册的地方是生成器，不是生成物**。两票的用例措辞都是交付时的原文，本票没有改动它们的内容。

生成器的计数口径也一并修正：状态列带限定语的通过（`PASS（UT）`——通过了，但证据是单元测试而非系统测试）**确实执行且通过**，原口径只认字面 `PASS`，把这类行算进「待执行/未实现」。三份设计书的计数口径现在都是「总数 = 已执行通过 + 待执行」。

## 9. 已知边界

1. **工作台不代为打开 trace。** Trace Viewer 是引擎附带的独立程序，版本须与产生该 trace 的引擎一致。界面负责定位、校验与说明；打开与否由读者决定。
2. **Trace 定位依赖 `report.json`。** 报告缺失或无法解析的运行只能走兜底推导，而推导在**超长标题 / 多项目 / 重试**场景下不精确——此时报「定位不到」而不是猜。
3. **跨运行并排对照尚未在界面上提供。** 模块能力与接口基础已交付（P1）。
4. **附件的时间是文件修改时间，不是归档时刻**（§4.2）。
5. **摘要是归档时的摘要**；文件被改动后，界面仍显示归档值，差异由校验结果报出（§4.1）。两者不互相冒充。
6. **人工可用性（无障碍 / 键盘 / 加载态）未评测**，属 ATS-111。
7. **本工作台只覆盖本机 Bridge 的运行历史**，不含远程 Runner（属 ATS-502/ATS-503）。
8. **哈希在界面上以短形式显示**（前 12 位 + 省略号），完整摘要在 `title` 属性与附件表里——短摘要单独出现是无法核对的，所以完整值始终可取。

## 10. 与既有设计的关系

| 既有交付 | 本任务在其上的位置 |
|---|---|
| ATS-209 证据清单 | 提供**归档时的摘要**与篡改判定；本任务消费它，不重算 |
| ATS-208 执行模型 | 提供**用例身份**（文件+describe+标题+行号）与 attempt 模型；对照按它配对 |
| ATS-216 质量概览 | 共享模块的**做法**（一份实现、两个界面）与失败用例的来源 |
| ATS-101/102 端口与依赖基线 | 端口硬编码清单与 ADR 引用按新位置同步；门禁保持绿 |
