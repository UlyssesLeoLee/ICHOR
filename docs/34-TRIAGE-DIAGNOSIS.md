## 1. 为什么归因内核必须是确定性的

「AI 诊断」这条要求容易被读成「把报错丢给模型，让模型说是谁的锅」。本实现**不做**这件事，
因为它的结果**不可核对**：同样的报错，模型两次可能给出不同的归因，而验收标准要求
「每条推断附可核对来源」——一个不可复现的归因没有来源可核对。

因此归因内核分成两层，**各司其职**：

| 层 | 谁做 | 产出 | 可核对性 |
|---|---|---|---|
| **信号提取** | 确定性规则（本模块） | 从运行证据里读出事实 | 同一份证据 → 同一组事实 |
| **归因判定** | 确定性规则（本模块） | 分类 + 置信度 + 依据 | 每条依据都能指回一条事实 |
| 模型增强 | 可选，走 ATS-403 适配层 | 对同一组事实补充说明 | **本次未接入** |

模型增强是**可选叠加**在确定性判定之上的，不参与决定分类。这条顺序是刻意的：
分类错了，模型的话不能把它「圆回来」。

## 2. 分类：四类，且是封闭集合

验收标准要求「分类含脚本/产品/环境/不确定」。这四类是**封闭集合**
（`TRIAGE_CATEGORIES`），不多不少：

| 类别 | 含义 | 判据 |
|---|---|---|
| `script` | **脚本**问题：断言与被测行为不符，或用例本身写错了 | 断言类错误 + 被测文件在可疑变更里 |
| `product` | **产品**问题：被测代码的行为与需求不符 | 断言类错误 + 被测文件**不在**可疑变更里 |
| `environment` | **环境**问题：环境/依赖/网络/超时，与代码无关 | 超时、网络、浏览器缺失、依赖缺失等信号 |
| `undetermined` | **不确定**：证据不足以判定 | 其它一切，或关键事实缺失 |

### 2.1 为什么 `product` 需要「不在可疑变更里」这个条件

「断言失败」这件事本身**不区分**脚本错还是产品错：断言失败只说明「实际值 ≠ 期望值」，
至于期望值写错了还是实现错了，**断言文本里没有这个信息**。唯一能提供这个信息的是
**代码变更历史**：期望值所在文件在失败前被改过，指向脚本；没被改过，指向产品。

因此 `script` 与 `product` 的区分**依赖可疑变更检测**，而可疑变更检测**依赖 Git 历史**
（见 §4）。没有 Git 历史可比时（例如只有一次运行、没有基线），判定**降级为 `undetermined`**——
不是降级为 `product`。理由：把「没有证据」当成「证据指向产品」，会让归因系统在没有证据时
系统性地冤枉产品代码，而「冤枉」正是这个模块存在的意义所要避免的。

### 2.2 `environment` 优先于其余三类

超时与网络错误**看起来**像失败，但它们不区分脚本与产品——环境坏了的时候，两种代码都跑不起来。
所以 `environment` 的判定**先于**其它三类，且一旦命中就不再考虑脚本/产品。

### 2.3 什么才是承重的

**分类顺序本身不是承重的**：`environment` 分支覆盖的失败种类（`timeout` / `network`）与
断言类分支覆盖的种类（`assertion` / `element` / `navigation`）**互不相交**，因此把这两个
分支对调，**任何一个输入的分类结果都不变**。这一点由
`tools/ats410-probes/probe-triage-boundary.mjs` **实测**（不是断言）——把两个集合列出来，
交集为空。

真正承重的是**历史闸门**：断言类失败在没有可比的 commit 历史时必须落在 `undetermined`，
而不是 `script` 或 `product`。把闸门去掉（把「没有历史」当成「没有可疑变更」），
探针实测这 6 个输入的分类**全部改变**——每一个断言类失败都会被归咎于某一方。

因此「没有证据 = 不归咎」这条性质是有实测支撑的，而「顺序是契约」这句更强的话
**不成立**，本文件按实测口径写。

## 3. 证据引用：每条推断都要能被核对

每条归因结论带一个 `evidenceRefs` 数组，数组里的每一项是一个**可核对的对象**，
不是一句描述。每一项带：

| 字段 | 含义 |
|---|---|
| `kind` | `run` / `case` / `artifact` / `commit` —— 证据的种类 |
| `ref` | 该证据的标识（run id / case key / artifact 相对路径 / commit sha） |
| `digest` | 该证据的 SHA-256（`commit` 除外——commit 本身就是它的标识） |
| `detail` | 人读的说明 |

**规则**：

- 结论**不得**没有证据引用。`validateTriageReport()` 对没有 `evidenceRefs` 的结论报
  `TRIAGE_EVIDENCE_REQUIRED`。
- 证据引用**必须指向本次归因所依据的那次运行**。引用一个不在 `scope.runs` 里的运行
  报 `TRIAGE_EVIDENCE_OUT_OF_SCOPE`。
- 证据引用**不得**指向不存在的用例或文件。引用一个 `case` 但本次运行的用例列表里没有它，
  报 `TRIAGE_EVIDENCE_NOT_FOUND`。
- 证据引用里**不出现**本机绝对路径。`ref` 一律是相对引用或标识符。

「每条推断附可核对来源」这条验收标准由这四条规则承重：一个读者拿着 `ref` 能回到
那一次运行、那个用例、那个文件，并自己核对 `digest`。

## 4. 可疑变更：同一用例跨运行比对

「可疑变更」的定义是**具体的**，不是「最近有人改了代码」：

> **可疑变更**：在两次运行的 `gitCommit` **不同**的前提下，失败用例所在的测试脚本文件
> 在两次提交之间**发生过改动**。

三条规则，各自有理由：

1. **只比对同一个用例**。跨运行比的是**同一个逻辑用例**（`testKeyOf()` 的键：文件 + describe
   路径 + 标题）。不同用例之间没有可比性。
2. **两次运行的 commit 必须不同**。commit 相同就意味着代码没变，两次结果不同是 flaky，
   不是变更引起的——这一点 `evidence-workbench.mjs` 的 `compareRuns()` 已经用 `sameCommit`
   表达了，本模块沿用同一口径。
3. **只看测试脚本文件**。产品代码的变更**不**是「可疑变更」——它可能是修复，也可能是引入
   缺陷，正是归因要判断的对象，把它当成「可疑」会把判据变成同义反复。

### 4.1 差异建议

当两次运行的 commit 不同、同一用例在两次之间**从通过变成失败**时，模块给出**差异建议**：
「这次失败与 commit 之间的改动有关」。建议里带**改动文件列表**——那是可核对的来源。

建议**不包含**任何修复动作，也不包含要修改的断言。改断言是 ATS-411（人工定性）与
平台侧评审的事。

## 5. 权限边界：归因不能改断言、不能提交

FR-025 明确「**不能**自动修改断言或提交」。这在本实现里**不是一条约定**：

- 归因模块**不 import 任何写入接口**。它读运行的记录（`state.json` 里的 run）、读 Git 历史、
  读证据清单，**不写任何文件**。
- 归因内核所在的 `server/ai/triage.mjs` **不含 `node:fs` / `node:child_process` 的写路径**：
  Git 历史由**注入的** `gitReader` 提供，模块自己不 spawn 任何进程。这条性质由
  `tools/ats410-probes/` 的静态检查守护（带负控）。
- 归因报告里**没有**「修改断言」「更新 expected」「提交」这类字段。提案的落地路径
  在 ATS-401 的契约层就已经不存在（`server/index.mjs` 没有写入提案的端点），
  归因报告同样不提供这样的路径。

## 6. API 面

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/ai/triage/contract` | 契约描述：分类集合、判据顺序、证据引用规则、可疑变更定义、权限边界 |
| POST | `/api/ai/triage` | 对一次运行做归因。**只读**：不写仓库、不改断言、不提交 |

`POST /api/ai/triage` 的请求体：

```jsonc
{
  "runId": "run_1_<24 hex>",     // 必填：被归因的运行
  "baselineRunId": "run_1_…",    // 可选：比对基线（用于可疑变更）
  "projectId": "proj_1_…",       // 可选：显式指定项目（缺省按 run 归属推导）
  "consentId": "consent_…",      // 可选：模型增强时的外传授权（本次未用到）
  "modelEnhanced": false         // 可选：是否请求模型增强（未配置提供商时报错，不静默忽略）
}
```

响应：

```jsonc
{
  "contract": "triage/v1",
  "runId": "run_1_…",
  "gitCommit": "abc1234",
  "findings": [{
    "caseKey": "…", "title": "…", "file": "…", "line": 42,
    "category": "script|product|environment|undetermined",
    "confidence": 0.6,
    "basis": "…",                      // 判定依据（人读）
    "evidenceRefs": [{ "kind": "…", "ref": "…", "digest": "…", "detail": "…" }],
    "suspectChanges": [{ "file": "…", "from": "…", "to": "…", "commits": ["…"] }],
    "diffSuggestion": null | { "…": "…" }
  }],
  "summary": { "byCategory": { "script": 1, "product": 0, "environment": 0, "undetermined": 2 } },
  "checks": [{ "name": "…", "ok": true, "detail": "…" }],
  "modelEnhanced": false
}
```

`checks` 是**对账**：报告里的每一条结论都能回到那次运行的用例列表，每一条证据引用都能
被核对。计数对不上时报告 `ok: false` 并说明差在哪——不是悄悄抹平。

## 8. 未实现与未验证

| 项 | 状态 | 说明 |
|---|---|---|
| 用真实模型端到端验证归因 | **未验证** | 本机没有配置模型提供商，也没有真实凭据；`modelEnhanced: true` 会因没有提供商而报错，**不**静默退化成确定性结果 |
