# ATS-206 — JSON state 安全导入迁移、备份与回滚

> 交付物：**数据迁移 CLI**。验收标准：**v0.1 旧数据迁移后项目/历史数量一致；失败可还原**。
> 关联要件：NFR-008（恢复能力）、NFR-010（可靠性：数据库原子写入；避免操作时半写入）。
> 前置依赖：ATS-205（SQLite 元数据层）。状态：待审核。

---

## 1. 范围

ATS-206 交付**一个数据迁移 CLI**（`tools/migrate_state.mjs`）与它背后的迁移内核
（`server/migration/`），把 v0.1 的 `state.json` 迁移到当前方案，并保证两件事：

1. **迁移后项目/历史数量一致** —— 迁移不得丢项目、不得丢历史、不得丢用例登记、
   不得丢重试与产物；
2. **失败可还原** —— 迁移失败时数据目录回到迁移前的状态，且备份与回滚可用。

交付物同时覆盖两件此前无人负责的事：

* **安全导入**：`state.json` → SQLite 元数据层的导入必须是**可验证的**
  （镜像必须与状态一致才允许落库）；
* **备份与回滚**：迁移前必写备份，失败自动回滚，显式回滚命令可用。

## 2. 背景：一次迁移为什么会丢数据

迁移 v0.1 状态本质上是**重写标识符**：

| 旧 | 新 |
| --- | --- |
| `proj_<uuid>` | `proj_1_<24 hex>`（由项目根路径派生） |
| `run_<uuid>` | `run_1_<24 hex>`（由项目 UID + commit + 目标文件 + 序号派生） |

重写标识符有两种典型的丢数据方式：

* **丢字段**：迁移结果由一组**固定键**重建，迁移器不认识的键就被丢掉了。
* **丢可达性**：某张表以项目标识符为**键**。改了项目标识符却不改键，
  这张表**没有丢**，它只是**够不着了** —— 用新 UID 查会得到空。

第 2 种更隐蔽：文件照样能解析，Bridge 照样起得来，数据只是"不见了"。

### 2.1 实测确认的两处存量缺陷（ATS-201 的 `tools/migrate_uids.mjs`）

在实现前先做了复现探针（`docs/evidence/ATS-206/`），实测确认 ATS-201 的
迁移实现有两处数据丢失：

**缺陷 A：`trust` 映射被整块丢弃。** ATS-201 的 `planMigration` 用固定键重建
`nextState`，`trust` 不在其中（ATS-202 引入的信任闸门）：

```
newProjectUid      : proj_1_f44fd2bf5f0a074f897c0b52
trust in output    : <<ABSENT>>          ← 整个信任映射消失
```

后果：用户显式"背书"过的项目，在迁移后变回**未信任**，
权威发现对它永久回退到静态索引。

**缺陷 B：UID 登记表没有跟着改键，条目变得不可达。**

```
registry keys      : ["proj_11111111-1111-1111-1111-111111111111"]   ← 旧键
registry under new : <<NOT FOUND>>      ← 新 UID 下查不到
registry entries   : 0
```

后果：每个测试用例的稳定 UID 丢失，全部被重新分配 —— 已归档的运行证据与
用例关联断裂。

两处缺陷都不是"迁移失败"，而是"迁移成功但数据没了"。

> **缺陷 B 的范围。** 原表述"实测确认存量缺陷、所有用例 UID 丢失"**推断过度**。
> Bridge 写登记表时用的是 `projectUidOf(project)`（`server/core.mjs`），对旧项目
> 来说这个键**就是新的** `proj_1_` UID，因此真实的 v0.1→当前 Bridge 数据里
> **不会**出现以旧 id 为键的登记表。改键逻辑仍要保留 —— 它是**防御性**的：一份
> 以旧 id 为键的登记表（来自其他工具或手工编辑）在迁移后必须仍然可达，
> 否则它会静默变成空桶。
>
> 只有 `trust` 是真的以旧 id 为键（`projectUidOfTrust` 用 `project.id`），
> 缺陷 A 是实打实的存量缺陷。
>
> **夹具必须是真实的 v0.1 形状。** 验收用的 fixture 只带 `schema`/`projects`/
> `runs` 三个键，标识符是 uuid 形式；带 `uidRegistry`、`trust`、`attempts`
> 的 fixture 不是 v0.1 数据，测不出真实路径上的缺陷。

## 3. 设计

### 3.1 内核分层

```
server/migration/state-migration.mjs   纯函数：算迁移计划、计数、原子写
server/migration/apply.mjs             应用引擎：备份 → 写入 → 日志 → 失败自动回滚
tools/migrate_state.mjs                CLI：plan / apply / verify / rollback
tools/migrate_uids.mjs                 ATS-201 的工具，改为复用同一内核
```

**只有一个迁移实现。** ATS-201 的工具与 ATS-206 的 CLI 共用
`server/migration/state-migration.mjs`，两者不可能各自漂移 —— 这是修复上述
两处缺陷的前提：如果只在新工具里修好，旧的工具仍会丢数据。

### 3.2 迁移内核的两条规则

**规则一：不丢字段。** 迁移结果从**原状态的副本**开始，
内核显式改写的只有标识符、引用和以项目标识符为键的映射，
其余键**原样带过去**。未知的字段（未来的字段、插件加的字段）随迁移存活。

**规则二：以项目标识符为键的映射必须改键。** 目前有两张：

* `state.trust` —— 信任闸门（ATS-202），键是项目 UID；
* `state.uidRegistry.projects` —— 用例登记表（ATS-201），键是项目 UID。

改键规则（`rekeyProjectMap`）：

1. **非旧标识符的键原地保留** —— 它们已经是当前标识符；
2. **旧标识符的键迁到新名字**；
3. **新名字下已有值时，旧值不覆盖它** —— 当前值是较新的决定，
   用旧值覆盖等于撤销一个更晚的决定。

### 3.3 应用引擎：备份 → 写入 → 日志 → 回滚

一次迁移动的是**四份**状态：`state.json`、磁盘上的运行目录、SQLite 镜像库、
持久化的运行计数器。半途失败会留下互相矛盾的状态，
而**矛盾的状态比没迁移的状态更糟** —— Bridge 照常启动，照常读写。

因此引擎的顺序是：

1. **先算后写**：迁移计划与计数校验都在**第一次破坏性写入之前**完成；
2. **先备份后写**：每个将被覆盖的文件先复制成 `.bak`；
3. **写日志**：每一步成功后记进 `MigrationJournal`；
4. **失败自动回滚**：按**日志**（不是重算计划）逐步撤销已完成的步骤。

> 回滚由**日志**驱动而不是重算计划，是刻意的：重算会把本次运行**没做**的
> 事情也撤销掉（例如已经回滚过一次的那批目录），回滚于是变成第二次数据丢失。

写库这一步额外严格：镜像先写进临时库 `metadata.db.importing`，
**校验通过后**才替换正式库。校验不过的镜像**永远不会**被换上，
所以一次失败的导入不可能留下一个错误的镜像。

### 3.3.1 四条容易被忽略、但决定了成败的规则

前三条每一条都对应一个**真实发生过的数据丢失**；第四条决定锁的覆盖范围。

**规则一：备份与它所描述的那一次迁移同生共死。** `.bak` 里放的是
**某一次迁移之前**的状态 —— 只有和那次迁移配对，它才是可用的还原点。
两件事会让它失效：

* **`rollback` 成功之后**：备份已经被用掉了，它描述的那次迁移不再成立。
  这时备份被**归档**（改名 `state.json.bak.rolled-back`、`.rolled-back.1`…，
  永不覆盖），完成标记 `.migration-marker.json` 一并删除 —— 它描述的也是
  那一次迁移。**归档而不是删除**：运维随时可以回看它，但它不再是当前状态的
  备份，下一次 `apply` 会写一份新的。
* **`apply` 发现备份与当前状态不符**：这说明备份是**陈旧的** —— 它属于
  另一次迁移。此时备份同样先归档，再写入当前状态的备份。

  （第一次迁移之后、还没有回滚过的状态下，`apply` **不会**碰已有的备份：
  它仍然是 v0.1 原始数据的唯一副本。对**已迁移**的状态，`apply` 直接拒绝
  （`ALREADY_MIGRATED`），一个字节都不写；`--import-db` 单独对已迁移状态
  补镜像仍然可用。）

这条规则的**后果**是："apply → rollback → 记一个新运行 → apply → rollback"
这串操作里，**第二次 rollback 逐字节还原的是第二次 apply 那一份状态**，
中间记下的那个运行仍在状态里、其目录也没有变成孤儿。

若第二次 `apply` 时备份与当前状态**相同**，则保留原备份不另写 ——
两种情况都保证"还原点 = 迁移点"这一不变式。

**规则二：目录改名逐个记入日志。** 改名循环每改一个目录就往日志里追加一条并
**立即落盘**；`folders` 这一步在改名**开始之前**就记上。原因是：Windows 上
一个目录被资源管理器占用时改名会报 `EBUSY`，此时前面几个目录已经改了名。
如果只在改名全部成功后才记这一步，失败时日志里就**没有**任何改过名的记录，
自动回滚什么也改不回来 —— 状态文件回到了 v0.1，目录却还挂着新名字，
有若干个运行的证据不可达。

**规则三：中断可恢复，且以状态文件为准。** 日志（`.migration-journal.json`）在**第一次破坏性写入
之前**就落盘，迁移成功后才删除。所以进程被杀掉时日志还在磁盘上：

* `plan` 会报告"发现一次被中断的迁移"；
* 下一次 `apply` 读日志**补完**迁移（把目录改回状态文件所指的名字），
  成功后写一个完成标记（`.migration-marker.json`）；
* 日志若**无法解析**，迁移**拒绝**执行并保留该文件 —— 解析不出来的日志
  什么也没说，迁移无法知道状态文件是否已被写过，此时猜测比拒绝更危险；
* 中断发生在状态文件写入**之前**时，直接按日志撤销即可；
* **判断"迁移到底做没做"看的是状态文件，不是日志。** 日志记录的是被中断的
  那次运行**声称**做了什么；状态文件记录的是**实际发生了什么**。两者会不一致：
  进程若恰好死在状态文件的原子写与 `journal.done('state')` 之间，状态文件
  **已经是迁移后的**，日志却不知道。此时**绝不**报 `UNDONE`、**绝不**清日志 ——
  那样会把一个半迁移的目录说成"已经撤销"，而且清掉日志之后就没有任何东西
  记得这个目录不对劲了。恢复要么**补完**它（把目录改成状态文件所指的名字），
  要么**拒绝**并指向回滚，并且**保留日志**；
* 若某个运行的目录在旧名与新名下**都不存在**，恢复**拒绝**并保留日志 ——
  证据不可达时不能报成功；
* `dry-run` 在发现未完成日志时**只报告、不写入**，更不会去改目录名。

**规则四：锁在引擎内部获取，覆盖每一条写路径。**
`applyMigration`、`rollbackMigration` 都在**函数内部**取
Bridge 锁（`acquireBridgeLock`/`releaseBridgeLock`），且锁覆盖该引擎的
**每一次破坏性写入**：正常迁移、中断恢复、已迁移状态的 `--import-db` 导入、
回滚里的状态重写 / 运行目录改名 / 数据库恢复。只在 CLI 里读一下锁是不够的 ——
CLI 的读锁在读与写之间留了一个 TOCTOU 窗口，而且库调用方（不经 CLI 的调用）
根本不会被覆盖。`dry-run` 不取锁，因为它不写。

**锁在进程结束时是否被释放，取决于进程是怎么结束的。** 这两种情况必须分开说：

* **正常退出**（正常返回，或调用 `process.exit`）：引擎注册的**进程退出处理**
  会运行，把锁释放掉。进程不会把锁留在盘上。
* **被从外部杀死**（`SIGKILL` —— Windows 上是 `TerminateProcess` —— 断电，
  Ctrl+C）：**退出处理不会运行**，所以**锁会留在盘上**。留下的是一把
  **陈旧锁**（它的持有者已经不在了）。

陈旧锁不会挡住任何人：下一次运行会**接管**它（把锁文件改名让开、再删掉，
然后发布新锁）。接管的动作发生在新锁发布**之前**，所以那几次针对锁文件本身的
操作不在新锁的保护之下 —— 但**恢复过程中的每一次数据写入都在新锁下完成**。

这就是两种情况的分工：**退出处理负责"正常退出不留锁"，陈旧锁接管负责
"被杀之后下一次运行照样能安全地恢复"。** 恢复路径本身一直持锁，
它没有被陈旧锁拖下水。

### 3.3.2 回滚前的分叉检测

回滚会用备份**覆盖**当前的状态文件。如果状态文件在迁移**之后**又变了
（Bridge 又记了新的运行），回滚就会静默丢掉这些变化。因此迁移写下它
写入了什么，回滚在覆盖之前先比对。

比对的**不是字节，是清单**（`identityDigestOf`：项目与运行的集合）。
理由：Bridge 每次启动都会把它读到的运行的 `events` 写回状态文件，
所以**每次重启 Bridge 状态文件的字节都会变**，而历史其实一点没变。
按字节比对会让回滚在每次重启之后都被拒，运维每次都得用 `--force` ——
那 `--force` 就失去意义了。

清单变了就**默认拒绝**（退出码非 0），保留现有状态，并在输出里**点名**
会被丢弃的运行；只有显式加 `--force` 才强制回滚。判断"这个运行会不会被丢"
按**legacy 身份**比较：迁移会重写每个运行 id，直接比 id 会把**每一个**已迁移的
运行都误报成"会被丢弃"，回滚就永远被拒。

**只要回滚会丢掉运行，就默认拒绝 —— 这与有没有完成标记无关。**
上面的分叉检测依赖 `.migration-marker.json`，但标记不是回滚安全的**前提**：
用别的工具（例如 `tools/migrate_uids.mjs --backup`）迁移过的目录**根本没有**
标记，而它照样会被 `rollback` 还原 —— 此时在迁移之后记下的运行会被**静默丢掉**。
所以拒绝条件是 `runsLostByRollback` **非空**，与标记、清单无关，
输出里**点名**每一个会被丢的运行，只有显式 `--force` 才继续。

### 3.4 计数一致性怎么判定

验收标准是"项目/历史数量一致"。计数口径（`summarizeState`）：

| 计数 | 含义 |
| --- | --- |
| `projects` | 项目数 |
| `runs` | 运行记录数（历史） |
| `attempts` | 用例重试记录数 |
| `artifacts` | 产物记录数 |
| `registryEntries` | 用例登记条目数 |

迁移前后各算一次，逐项比对（`compareCounts`），不一致即**拒绝迁移**。
计数在**写入之前**算，因此拒绝不会留下任何痕迹。

### 3.4.1 项目 UID 撞车：迁移表示不了的状态必须直接拒绝

两个项目共用同一个 `root` 时，会导出**同一个项目 UID**。第二个会覆盖第一个：
它的用例登记条目、信任记录和计数器全部消失。计数比对能发现"条目数少了"，
但那已经是损失发生**之后**；而且丢的是哪一个项目的条目，从计数上看不出来。

所以撞车在**改键之前**就被拒绝，错误码 `PROJECT_UID_COLLISION`，并且
**点名两个项目**（`name`）与撞车的 UID：

```
the migration is refused: PROJECT_UID_COLLISION: the projects "app" and
"app-clone" both map to proj_1_c77e43e0a9c125f3ba9daf1e (the same root ...)
```

拒绝时状态文件逐字节未变。

### 3.5 CLI

```
node tools/migrate_state.mjs plan     [--data-dir <dir>] [--state <path>]
node tools/migrate_state.mjs apply    [--data-dir <dir>] [--state <path>] [--import-db] [--no-rollback] [--dry-run]
node tools/migrate_state.mjs verify   [--data-dir <dir>] [--state <path>]
node tools/migrate_state.mjs rollback [--data-dir <dir>] [--state <path>] [--force]
```

* `plan` —— 只报告，不写；
* `apply` —— 迁移；先写备份；失败自动回滚（`--no-rollback` 可关闭）；
* `verify` —— 校验 SQLite 镜像与状态文件是否一致；
* `rollback` —— 显式回滚：从备份恢复状态文件与数据库，并把运行目录改回旧名。
  会丢运行或状态已分叉时**默认拒绝**并点名，`--force` 才强制执行。

退出码：`0` 成功 / `1` 失败 / `2` 用法错误 / `3` Bridge 正在运行（拒绝迁移）。

**`--state` 的语义：它指名的文件就是被迁移（被回滚）的文件。**
四个命令都遵守这一条 —— 不是"`plan` 认、`apply` 不认"。

**失败一律是一行原因 + 退出码 1，不打栈。** 文件缺失、不是 JSON、
`PROJECT_UID_COLLISION`、损坏的日志、无可回滚的备份，都是这样。
CLI 是运维工具，栈对运维没有帮助。

**Bridge 运行中必须拒绝迁移与回滚。** Bridge 在内存里持有状态并在每次变更时写回，
迁移会被它的下一次写覆盖，而磁盘上的运行目录已经是新名字 ——
结果是状态指向不存在的目录。

`apply` 与 `rollback` 在**整个写入期间持有** Bridge 的锁
（`acquireBridgeLock`/`releaseBridgeLock`，与 `tools/migrate_uids.mjs` 一致），
不是只读一下锁就开写 —— 只读锁留了一个 TOCTOU 窗口，
Bridge 可以在读锁与写之间启动。这把锁是在**引擎函数内部**取的
（见 §3.3.1 规则四），因此库调用方同样受保护。

### 3.6 与 SQLite 元数据层的关系

`state.json` 仍是**唯一事实源**，SQLite 是它的**镜像**（ATS-205 的定位不变）。
`--import-db` 让迁移同时刷新镜像；不传该参数时迁移只动 JSON 与运行目录。

## 4. 已知边界

* **降级**不在本项范围：SQLite 的 down 脚本是显式有损操作（ATS-205 已定义），
  ATS-206 不为它提供自动回滚。
* **ATS-207**（单实例锁与 WAL 恢复）负责进程级的独占与断电恢复；
  ATS-206 只做**迁移过程**本身的原子性与可还原性。
* 跨**文件系统**的原子写不成立：备份与状态文件在同一个数据目录内，
  替换用 `rename`（同目录，原子）。跨卷不是本项支持的场景。
* 迁移是**离线**操作：必须先停 Bridge（CLI 会检查 `bridge.lock` 并拒绝）。
