## 2. 一份实现，两个界面

仓库里有两个用户界面：

| 文件 | 作用 |

## 3. 搜索口径

搜索在**三个字段**上进行，用**同一条规则**：大小写不敏感的子串匹配。

| 字段 | 例 | 说明 |
|---|---|---|
| 用例名 | `登录` | 命中 `用户登录`、`登录失败提示`，不命中 `登出` |
| 文件 | `cart.spec` | 命中 `tests/cart.spec.ts` 下的全部用例 |
| 标签 | `smoke` | 命中带 `smoke` 标签的用例（作者写 `@smoke`，引擎报 `smoke`） |

三条字段**一起搜**而不是分成三个条件：输入 `smoke` 的用户是在找带 smoke 标签的用例，
不管它在哪个文件；输入文件名的用户要的是那个文件里的用例。

**空查询不是过滤条件**：空搜索框保留全部用例。若把空查询当成「什么都不匹配」，
目录在用户打字之前就是空的。

**结果是清单的子集**：`filterCases()` 返回的是传入用例对象本身（保序），不会出现清单里
没有的用例（UT-ATS214-006 对多个查询断言了这一点）。

## 4. 标签口径

### 4.1 标签从哪来（实测）

Playwright 的 `--list` JSON **带标签**（`spec.tags`）。本机实测（真实 Playwright 1.64.1）：

| 源码 | CLI 报告 |
|---|---|
| `test('x', { tag: '@smoke' }, ...)` | `['smoke']` |
| `test('x', { tag: ['@a', '@b'] }, ...)` | `['a', 'b']` |
| `describe('g', { tag: '@group' }, ...)` 内的用例 | `['group', ...用例自己的标签]` |
| 嵌套 describe | 外层 + 内层 + 用例自己的，逐层累加 |
| 重复标签 | `['a', 'a']`（引擎不去重） |

两条必须记住的事实：

1. **CLI 要求标签以 `@` 开头**（否则整个文件被拒：`Error: Tag must start with '@'`），
   但**报告时不含 `@`**。所以比较标签时两边都去掉前导 `@`。
2. **describe 的标签被其内的用例继承**，逐层累加。

### 4.2 两个索引的标签必须一致

- **权威索引**：标签直接来自 CLI（`server/discovery/playwright-list.mjs` 解析 `spec.tags`）。
- **静态索引**：标签由本任务新增的词法读取器读出（`server/uid.mjs` 的 `scanCaseTags`），
  读 details 对象的 `tag`/`tags` 属性，并继承 describe 的标签。

如果静态索引不读标签，标签过滤就会在**可信项目上能用、未可信项目上永远匹配不到**——
这读起来像「过滤器坏了」，而不是「过滤器没看到标签」。所以静态索引也读。

**实测**：同一份夹具，静态索引与真实 CLI 的 `--list` 输出**逐条一致**（6 条用例，标签全同）
——见 `docs/evidence/ATS-214/03-tag-parity.log`。

### 4.3 不读计算式标签

`{ tag: someVar }` 不读。静态索引不求值代码，猜出来的标签会让过滤结果错配——
一个猜错的标签比一个缺失的标签更糟。

### 4.4 多标签的口径

勾选多个标签有两种可能的口径，一个不说清楚自己用哪种的界面就是在隐瞒：

| 口径 | 含义 | 集合运算 |
|---|---|---|
| `any`（任一） | 用例**至少**带一个被选中的标签 | 并集 |
| `all`（全部） | 用例**带全**被选中的标签 | 交集 |

**本任务默认 `any`（任一）**：标签过滤是「把标了这类的东西给我看」的功能，
读者勾两个标签时期待的是并集。`all` 也实现了，界面用「任一 / 全部」下拉标注当前口径。

两个口径**必须真的不同**（UT-ATS214-011 断言 `any` 4 条、`all` 2 条，且 `all ⊆ any`）。
若两者实现相同，「口径」就只是个装饰。

### 4.5 标签比较

- **大小写不敏感**：标签是标签，`Smoke` 与 `smoke` 对人是同一个标签。
- **忽略前导 `@`**：用户输入 `@smoke` 必须能找到引擎报告的 `smoke`。
- 列表**去重且有序**。

## 5. 集合语义（最容易做错的一条）

四个条件各自是一个**集合**，结果是它们的**交集**：

```
result = search ∩ tag ∩ file ∩ status
```

**不是并集**，也**不是「后一个条件替换前一个」**。

两种错误都是**静默**的——列表看起来仍然合理：

- **并集**：勾一个标签把列表**变宽**。UT-ATS214-016 用一个 2 条与 3 条的条件断言结果是 2 条
  而不是 3 条；UT-ATS214-017 用两个**互不相交**的条件断言交集为空，而并集会是 3 条。
- **替换**：清掉标签条件把搜索条件一起清掉。UT-ATS214-018 双向断言：清掉标签后搜索仍在，
  清掉搜索后标签仍在。

**每个条件各保留了多少条单独报出来**（`describeFilter()`）：因此「没有匹配」与
「交集为空」是可区分的——读者能看到搜索保留了 2 条、标签保留了 1 条，而交集是 0 条。
单看列表分不出这两件事。

筛选后的**顺序是目录的顺序**：列表是目录的一个视图，不是重新排序的结果，所以筛选不会
改变用户看到的顺序。

## 6. 选择集合

### 6.1 它是一个集合

选择是**用例 UID 的集合**：勾选的顺序不是它的一部分，两次相同的勾选产生完全相同的快照
（UT-ATS214-025 / UT-ATS214-028）。

### 6.2 快照是自含的

`selectionSnapshot()` 产出的记录带每条用例的**文件、标题、行号**：

```
{ uids: [...], cases: [{uid, file, title, line}, ...], count, unknown }
```

自含的理由：目录每次轮询都会重读，用例可能已被改名、移动或删除。只记 UID 的记录，
过一会儿就变成一份没人读得懂的标识符列表。

### 6.3 目录不认识的 UID 被**报告**，不被静默丢弃

`unknown` 列出目录里没有的 UID（UT-ATS214-027）。调用方据此**拒绝**整个选择：
静默跳过会得到一次覆盖更少用例的运行，而运行记录却会说自己覆盖了全部——
选择就成了主张而不是记录。

### 6.4 按文件分组

引擎每次只接受**一个**测试文件过滤参数（ATS-106 的参数基线拒绝第二个位置参数），
因此跨文件的批量运行必须按文件拆开。分组是选择语义的一部分，界面上先显示
「将分 N 个文件依次执行」，再让用户按下按钮。

## 7. 批量运行

### 7.1 请求

`POST /api/projects/:id/run` 新增**一个**可选字段 `selection`（用例 UID 数组）。
ATS-106 的白名单机制保持不变：`file` / `capabilities` / `runner` / `env` / `selection`
之外的任何字段仍以 `400 RUN_PARAMETER_NOT_ALLOWED` 拒绝。

| 情况 | 响应 |
|---|---|
| `selection` 不是数组 | `400 SELECTION_NOT_AN_ARRAY` |
| `selection` 是空数组 | `400 SELECTION_EMPTY` |
| 有 UID 不在目录里 | `400 SELECTION_UNKNOWN_CASE`（附 `unknown` 数组） |
| 正常 | `202`，运行记录带 `selection` 与 `selectionUids` |

**有选择时 `file` 由选择决定**（第一个分组的文件）：调用方同时送 `file` 和 `selection`
会有两个事实来源，而它们可以互相矛盾。

### 7.2 批次链

选择跨多个文件时，它是一个**批次**：每个文件一次运行，前一个到达终态后启动下一个。

链在**运行结束时**推进（`advanceBatch()`），而不是靠定时器或轮询：下一个运行不能在前一个
还持有项目时启动（Bridge 拒绝同项目第二个运行），而「运行结束」正是前一个已确定释放项目
的那一刻。定时器只能**猜**项目什么时候空出来。

被**取消**的运行会终止链：用户要求停止，继续跑下一个文件等于跑用户已经不要的用例。

批次记录（`batchUid` / `groups` / `runs`）说明选择被怎样拆分、每个文件做了什么。

### 7.3 「选了什么、跑了什么」可复现

运行记录里的**选择集合**与本次运行的 **attempt** 是两条**独立**的事实：

- 选择集合：运行开始时的快照（哪些用例、各自的文件/标题/行号）
- attempt：引擎实际跑出来的、绑定了 UID 的执行记录

**每一次运行只记录它自己那一组**。跨文件的批次被拆成若干次运行，每次运行的选择集合
是**该组**的选择，不是整个批次的。所以 run#1 的对账卡不会把 run#2 的用例算成「缺失」
——第一版把整个选择集合写进了 run#1，于是每个跨文件批次的 run#1 卡片都报红色的
「选中但未执行」。

界面的对账表逐项列出：

| 核对项 | 含义 |
|---|---|
| 选中用例 | 运行记录里的选择集合（该组） |
| 实际执行的用例 | 本次运行的 attempt 绑定的 UID |
| 选中但未执行 | 缺失——引擎没跑，或身份映射器绑不上 |
| 执行但未选中 | 多跑——引擎按文件跑，会跑该文件里的其它用例 |
| 选择可复现 | 选中的用例是否全部执行 |

**多跑不破坏「可复现」**：选择集合仍然就是用户选中的那几条。但它必须被看见——
「我选了 3 条，跑了 5 条」是读者需要知道的事实。

### 7.4 批次级的对账视图

每次运行只能报告它自己那一组，所以**批次**另有一张表：「选了什么 / 跑了什么」针对
**整个选择集合**。`GET /api/batches` 返回批次的选择集合、每个 run 的状态、以及一份
由**运行记录**算出来的对账（`reconciliation`）。

界面（执行中心）按批次列出：选中、实际执行、选中但未执行、执行但未选中、结论。
第一版里 `batches` 是**死状态**——读了不写、写了不读，批次级的对账在界面上根本不存在。

### 7.5 批次继承请求上下文

批次的**每一个**运行都在与第一个相同的条件下启动：环境档案、pinned runner、请求的
capabilities。批次记录里存着这份上下文（`batch.context`），每个 run 把它写进自己的记录。

理由不是方便：**ATS-212 禁止静默回落到「无档案」**。一个批次里第一个 run 跑 staging、
第二个 run 跑默认 base URL，那正是这种静默回落，只是摊在了两次运行上，而读运行记录的
人分不出它与两次有意为之的运行。

#### 批次记录只存档案的**引用**，不存变量的值

`batch.context` 里存的是档案的**标识**（`envUid` / `envName` / `envTier`），**不是**
档案的变量值。原因有二，两者都是硬要求：

1. **值不能出现在记录里。** 批次记录会被归档、镜像进 SQLite、随证据包分发。一个变量的
   值出现在里面，就意味着 `GET /api/batches` 会把它交给调用方——档案值因此从
   「运行配置」变成了「API 出口」。
2. **白名单必须约束运行，而不只是写入。** 白名单在档案写入之后被收紧时，之后才启动的
   run 必须**不再**带着那个变量。若批次把过滤后的变量**快照**下来再继承，快照就会把
   白名单已经收走的变量带回来——白名单于是退化成一次写入检查。

因此**每个 run 在启动时重新解析那份引用**（`batchRunEnv`）：

- 档案按项目自己的档案库查（`findProfile` + `projectKeyOf`），找不到就是**事实**：
  批次以 `ENV_PROFILE_NOT_FOUND` 结束，而不是静默地退化成「无档案」运行；
- 变量按**当前**白名单过滤（`filterProfileVariables` + `whitelistForProject`），
  与单文件路径是**同一个函数、同一个白名单来源**；
- 凭据引用在**运行时**才解析（`resolveCredentialRefs`），因此密钥同样不随批次记录旅行。

被白名单收走的变量记在 run 的 `envRefused` 里（名字与理由），到达 runner 的变量名记在
`envVariables` 里——**只有名字，没有值**（ATS-212）。

#### 档案被删除时批次如何结束

档案在批次进行中被删除，后续 run 不会「就那样跑下去」：它以
`ENV_PROFILE_NOT_FOUND` 结束批次，批次状态 `failed` 且带原因。读者看到的是
「因为档案没了所以没跑」，而不是一个悄悄换了环境的运行。

### 7.6 批次必达终态

批次永远 `running` 比失败的批次更糟：它声称有工作在飞，而实际上没有，读者也分不出来。
因此**每一条**结束一个 run 却没有推进链的路径，都同时结束批次：

| 路径 | 批次的结果 |
|---|---|
| 预检失败（没有引擎等） | `failed`，带原因 |
| `adapter.start` 抛错 | `failed`，带原因 |
| 某组被 ATS-106 的过滤检查拒绝 | 整单 `400 INVALID_TEST_FILTER`，**在启动任何运行之前** |
| 链无法启动下一个运行 | `failed`，带原因 |
| Bridge 在批次进行中重启 | `interrupted`，带原因 |

「某组被拒绝」这一条有两个实现细节：

1. **批次建立时对**所有**分组做 `readSource` + `assertSafeTestFilter`**，任一组被拒就整单
   拒绝。与单文件路径**同一个错误码**，两条路径不能对同一个文件给出不同的答案；
2. **批次在第一个 run 启动之前建立**。第一版是先 `startRun()` 再建批次，所以预检失败时
   根本没有批次可以结束，批次永远 `running`。

## 8. 500 用例：布局与响应预算

完成定义的第一个分句是「500 用例过滤无明显阻塞」。这一条有两个面：**算得快**与
**看得见**。

### 8.1 布局：筛选区必须有界

第一版把每个标签、每个文件都渲染成芯片，装在一个会自动换行的列表里。50 个文件时，
FILES 区本身长到 **858px**，把用例列表推到 **1189px**——**在 900px 的视口之下**——
读者看不到、也点不到任何一条用例。列表在，可达性没了。

因此芯片列表**有界**：`.tag-list`（以及便携 UI 的 `.chips`）有 `max-height:180px` 与
自己的滚动条。筛选块因此永远只占它该占的那点高度，用例列表始终有可用的份额。

### 8.2 响应预算

预算**事先写明**（写在探针的源码里，先于任何一次运行）：

- 单次交互在 **100ms** 内得到响应；
- 没有超过 **100ms** 的 long task。

实测在真实 Chromium、真实 Bridge、500 用例 / 50 文件的夹具上进行，覆盖：逐键输入、
**清空查询**、标签口径切换、「全选当前」、取消勾选。4 倍 CPU 降速下的数字**只作参考**——
降速的 CPU 是另一台机器，为真实机器写的阈值不能被静默地套到它身上。

**「清空查询」也在预算之内**，它不是「前置步骤」而是**读者能触发的最大一次 DOM 变化**：
它把列表从 110 行变回 500 行，一次绘制挂上 390 行（5850 个 DOM 节点）。
ST-ATS214-003 把它算进预算，ST-ATS214-010 之后的每一次复跑都会报出它的数字。

证据：`docs/evidence/ATS-214/10-st-500-cases.log`。

### 8.3 选择框必须键盘可达

第一版的勾选框是 `<button>` 里嵌的 `<span role="checkbox" tabIndex="-1">`：浏览器把
tab 站点给外层的 button，内层的勾选框**永远拿不到焦点**，键盘用户根本无法勾选。

现在行是 `<div>`，勾选框是**自己的** `<button role="checkbox">`，打开用例是另一个
`<button>`。每一个控件都是一个控件，每一个都可达。

## 9. 「选中准确映射 UID」

### 9.1 选择与 UID 的对应关系

选择是 UID 的**集合**（§6.1），快照自含（§6.2），目录不认识的 UID 被报告而不是静默
丢弃（§6.3）。运行请求带的就是这些 UID，Bridge 对照目录校验它们。

### 9.2 离开目录的用例必须**显式**处理

用例被改名、移动或删除之后，它就不再在目录里了。第一版这时**静默地**把计数从 2 变成 1，
页面不给任何提示，批量运行按 1 条提交——「选中准确映射 UID」在这里被打破了，而且是无声的。

现在：

- 共享模块的 `selectionDiffs()` 算出「已选但不在目录里」的 UID；
- 界面**显示**它们（`role="alert"`，屏幕阅读器会播报），并给一个「移除这些用例」的按钮；
- **运行被阻止**，直到读者处理掉它们。

### 9.3 选择按项目隔离，切换项目时重置

UID 是**某个项目里**一条用例的身份。跨项目保留的选择指向的是另一个项目的 UID，
「已选 N 条」数的是读者看不见、也不会跑的用例。

切换项目时**过滤条件与选择一起重置**，并且**告知**读者重置了什么——无声消失的条件，
读者还会再找一次。

### 9.3 500 个用例时的响应预算

「500 用例过滤无明显阻塞」里的「阻塞」不只是「点得动」，还包括「点了之后多久有反应」。
实测的预算事先写明：**单次交互 ≤ 100ms，且没有 > 100ms 的 long task**。

把这条预算顶破的都是**渲染**的问题，不是检索的问题（检索本身是 O(n)）：

| 做法 | 代价 | 改法 |
|---|---|---|
| 每行问两次「这条勾上了吗」，用 `Array.includes` 线性扫描 | 500 行 × 500 个已选 UID × 2 次 = 每次渲染 50 万次字符串比较 | 勾选状态存成 `Set`，一次查询 O(1) |
| 选择记录**每个已选用例一行表格** | 勾选 500 条时多出 501 个 `<tr>`、4000+ 个 DOM 节点，浏览器排版就把交互推到 100ms 之外 | 选择记录**按文件分组**，每组只列前几条（选择集合本身仍是完整的快照） |
| 用例行内联在列表里 | 勾选一条 → 500 行全部重渲染 | 行拆成记忆化的组件；勾选状态与标题分成两个组件，标题那一半不随勾选重渲染 |
| 勾选状态经过**行的 props** 传递（`ticked={selectedUidSet.has(t.uid)}`） | 每一次勾选都重新渲染**行**；「全选 500」重新渲染 500 行 | 勾选状态改为经过一个**只有勾选框消费的 context**：行的 props 不变（行不重渲染），只有 500 个勾选框重渲染，每个只是一个节点 |

最后一条实现的是行上原来就写明的意图：`React.memo` 在行上原来是失效的，
因为 `ticked` 每次都变。改成 context 之后，行不再重新渲染，而勾选框仍然重新渲染
（它们消费了新的 context）。

**实测（CDP 计数器，8 轮交替的 A/B）：这一改动在预算上是中性的**——
“全选”的 script 时间中位数 16.1ms → 16.0ms，“清空查询”的 24.6ms → 24.9ms。
它不是一个性能修复，而是把原来写在代码里的意图真正做到。

`aria-checked` 仍然是**从状态渲染**的——可访问性树不是手工打补丁的。
ST-ATS214-012 在真实浏览器里检查这件事：勾一个、再勾一个、全选、
再取消一个，数字与 `aria-checked` 都跟着状态走。

### 9.4 文案如实

引擎每次只接受一个文件过滤参数，而文件过滤会跑该文件的**全部**用例。所以「选中 1 条」
实际会跑 3 条。第一版的 toast 写「已提交运行：1 个用例」，而引擎跑了 3 条——界面在
承诺精确选择。

现在界面说的是**实际会执行的条数**：

- 选择栏：「已选 1 条 · 将执行 3 条」；
- 提交后的 toast：「已提交运行：选中 1 条，实际执行 3 条，同文件的其余用例也会执行」。

共享模块的 `plannedExecutions()` 是这个数字的**唯一**来源。

## 10. 已知边界

1. **没有「按 UID 精确执行单个用例」**。适配器的 `filterByTestUid` 能力仍为 `false`
   （ATS-301 登记的既有缺口），所以跨文件批量运行时引擎会跑该文件内的**全部**用例；
   多跑的用例由对账表报出，界面也如实说明会执行多少条。实现这一条需要改适配器契约
   与运行参数基线，超出本任务范围。
2. **计算式标签读不到**。经变量、函数或配置计算出来的标签读不到（静态索引不求值代码）。
   **标题里的标签读得到**——见 §4.1。
3. **状态过滤在本任务里没有数据源**：用例在跑过之前没有状态。共享模块提供了
   `statusOf` 回调入口与该条件，但没有界面使用它。
4. **人工可用性（无障碍 / 加载态）未评测**，属 ATS-111。勾选框的键盘可达性由
   ST-ATS214-010 实测（§8.3）。
5. 只在 Windows 11 + Node 24.19.0 + Chromium 上实测，未在 macOS / Linux 上跑过。
