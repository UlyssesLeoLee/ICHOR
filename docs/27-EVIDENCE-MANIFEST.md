# ATS-EVD-001 证据清单与保留策略设计书（ATS-209｜S2 / v0.2.0）

> 本文描述 **Evidence Manifest、SHA-256、去重/保留策略**的交付内容。
> 数据字典见 `docs/06-DATA-DESIGN.md` §4，接口面见本文 §5。

## 1. 这一项交付的是什么

ATS-209 的交付物是「证据索引与清理器」：一次运行留下的证据文件（JSON 报告、HTML 报告、
trace 归档、截图、录屏）有一份**可校验的清单**，清单带着每个文件的 SHA-256；证据的字节
**只存一份**；到期��证据可以被清理，而**运行元数据不会被误删**。

两个验收标准与实现位置的对应：

| 验收标准 | 含义 | 实现 |
|---|---|---|
| 篡改可检测 | 归档后被改动的文件必须被发现，并指名是哪个文件 | `server/evidence/manifest.mjs` 的 `verifyEvidence()` |
| 保留期到期可清理且不误删 Run 元数据 | 到期的证据被移除，run 记录（状态、summary、attempts、events）原样保留 | `server/evidence/retention.mjs` 的 `cleanExpiredEvidence()` |

## 2. 交付前的实测状态

交付前的行为由 `tools/ats209-probes/` 下的探针**实测**，不是推断。下面是交付前后的对照
（同一份夹具、同一台机器）：

| 场景 | 交付前（实测） | 交付后（实测） |
|---|---|---|
| 运行结束后 `manifest.json` 的内容 | `{version:1, runId, artifacts:[{file,size,sha256}], attempts}` | `{version:2, runId, projectUid, sourceCommit, artifacts:[...], attempts, evidence:{count,totalBytes,setDigest}}` |
| 清单是否说明 digest 属于哪个 run | **否**（只有 `runId` 一个字段，digest 不带归属） | **是**（`runId` + `projectUid` + `sourceCommit` + `evidence.setDigest`） |
| 归档后文件被改动 | **无人检查**——digest 记下了，但再也没被读过 | `GET /api/runs/:id/evidence` 报出 `changed[]`，含应有与实际两个 digest |
| 归档后文件被删除 | **无人检查** | 报出 `missing[]`（与 `changed[]` 分开，不是同一件事） |
| 相同内容的证据（重跑同一失败用例） | 存**两份** | 存**一份**：run 文件成为 store 中副本的硬链接 |
| 到期清理 | **不存在**——run 目录无限增长 | `tools/evidence_retention.mjs clean` 移除证据，保留 run 记录与事件日志 |
| 清理与 Bridge 并发 | 不存在此问题 | **拒绝**：Bridge 持有数据目录锁时清理退出码 3 |

**manifest 的版本从 1 升到 2**：v1 的清单没有 `evidence` 段，也没有 `projectUid` /
`sourceCommit`，因此无法回答「这组 digest 属于哪一次运行」。v2 补上这两项，`version` 字段
随之递增，读旧清单的代码能据此判断版本。

## 3. 三者的边界

### 3.1 清单（manifest）：归档对自己的记录

清单是**运行记录与文件夹内容**的函数：同样的运行、同样的文件，总是得到同样的清单。
这正是它可被校验的前提——读者可以重建一份清单再比对。

清单里的每条证据是 `{file, size, sha256}`：

- `file` 是**相对 run 目录**的路径，用 `/` 分隔（跨平台一致）；
- `sha256` 是文件**原始字节**的摘要。**不做任何归一化**：忽略了行尾差异的摘要检测不到
  「文件被改写成了另一种行尾」，而那正是证据文件必须能发现的改动；
- `size` 是字节数。两个同名同摘要但大小不同的文件不是同一份证据，所以 size 参与
  `evidence.setDigest` 的计算。

清单**不列出自己**，也不列出 `events.jsonl` 与 `stdout.log`：后者是运行的**记录**，前者是
证据的**记录**，三者分开，清理器才能只动证据。

**清单与 run 记录覆盖同一个文件集合**。两处用的是**同一个收集器**（`collectEvidence`）与
**同一个上限**（`MAX_EVIDENCE_ENTRIES`，400）：run 记录的 `artifacts[]` 与清单的 `artifacts[]`
因此永远一致。曾经不是——两处各走各的、各有各的上限，于是证据超过 400 个文件时，清单只覆盖
其中 400 个（`html/data/*` 按目录序先占满了名额，`report.json` 落在外面），而 run 记录知道全部：
**清单外的文件不受篡改检测保护**。现在上限是两者共用的，且**触到上限时清单会写明**
（`evidence.truncated`），校验因此**判失败**——一份没有覆盖全部证据的清单不是可校验的清单。

**截断的豁免很窄**：只有当文件夹里**再没有**清单未列出的证据文件时，截断才被豁免（那些文件
已经被清理掉了，没有留下不受保护的东西）。一条清理记录本身**不能**豁免截断——否则一份丢了
52 个文件的清单会被一条只提到其中 1 个文件的清理记录豁免掉，另外 51 个留在盘上的文件仍然在
篡改检测之外。清理器移除「清单未列出的文件」时**不受条目上限约束**，所以被截断的那批文件
同样会被清理干净。

`evidence.setDigest` 是整组证据的摘要（对排序后的 `file:sha256:size` 行取 SHA-256），
所以两份证据集合相同的运行会得到同一个 `setDigest`——去重与比对都以此为依据。

### 3.2 去重：字节只存一份

去重不是「报告重复」，而是**真的只存一份**。

`server/evidence/store.mjs` 是一个**内容寻址存储**：证据文件的字节按自己的 SHA-256 存在
`<data-dir>/evidence-store/<前2位>/<第3-4位>/<摘要>` 下，run 目录里的文件则变成指向该副本的
**硬链接**。

用硬链接而不是副本，原因有两：

1. **空间**：副本仍然占空间，硬链接不占——字节在磁盘上只有一份，最后一个链接消失时空间才回收；
2. **原子性**：链接先在临时名下建立，再 `rename` 覆盖目标，读者不会看到装了一半的文件。

**硬链接不提供什么（必须写明）**：篡改检测依赖的是**清单里的摘要**，不是硬链接。摘要是归档时
算下的，校验时重算并比对，两次不一样就报出来。硬链接带来的是另一个性质——**一次就地改写的
影响面会被放大**：经一个链接就地写入的内容对所有共享该 inode 的链接可见，因此改写一个 run 的
证据文件会同时改掉其他共享同一份内容的 run，那些 run 都会被报为 `changed`。这是检测**如实**
报出来的，不是误报，但它说明**store 的副本不是独立备份**：与 run 文件共享 inode 的副本会被
run 文件的改动一并改掉。

**复用已有 blob 前先校验其内容**（`storeBlob`）：blob 已存在时**不信任**它，重新算一遍摘要与
它所在的名字比对；不一致就**用正确的字节替换掉**。理由是上面那条放大效应：一个被就地改写的
blob 若被直接复用，之后每一个产出相同内容的 run 都会链接到这份被篡改的字节——一次篡改就会毁掉
之后**每一个**产出相同内容的 run，而且篡改检测会把被污染的那个 run 报成元凶。

不能链接的情况（跨卷、文件系统不支持链接、超过体积上限）被**如实报告**而不是静默忽略：
证据照常归档、照常可校验，只是没有去重，原因记在 run 的 `dedupRefused` 上。

**去重的诚实边界**：一个 run 目录若少了文件，它就不再与自己的清单相符。索引因此**不替活着的
run 删文件**——它**记录**哪些内容被存了多份、哪一份是最先登记的。**索引不替清理器决定删什么**：
清理器删除的是到期 run 的**全部证据**，与索引无关；索引也不会「保留权威副本」——到期的证据
一律删除，哪怕别的 run 恰好持有相同的字节。活着的 run 必须始终能出示自己的证据。

**字节数的含义**：去重报告里的 `sharedBytes` 是「同一份内容若按每个 run 各存一份会占多少字节」，
**不是**磁盘浪费的字节数——重复副本是硬链接，字节在盘上只有一份。磁盘实际占用由 `storeBytes`
给出（它量的是 store 本身）。旧的字段名 `wastedBytes` 保留，值与 `sharedBytes` 相同。

### 3.3 保留：清理证据，不动元数据

这是本项最要紧的一条，代码按它来写：

- 清理器操作的是 **run 目录里的证据文件**，不碰 `state.json`、不碰 SQLite 镜像、
  不碰 run 记录的任何一个字段；
- run 目录里的 `events.jsonl`、`stdout.log` 与 `manifest.json` **保留**：前两者是运行的
  记录，第三者是「证据曾经是什么」的记录；
- run 记录本身（状态、summary、attempts、events）在 `state.json` 里，**根本不在 run 目录里**，
  所以清理器碰不到它。集成测试 `IT-EVD-108` 逐字段比对了清理前后的 run 记录。

**清理器只碰 run 目录以内的文件**。清单里指向 run 目录之外的条目（`../<另一个 run>/events.jsonl`、
`../../state.json`）被**拒绝并记录**——run 目录是 runner 的输出目录，`interrupted` 的 run 与启动
失败的 run 从不由 Bridge 写清单，那里的 `manifest.json` 是谁写的就是谁的；照着它删文件会删到
别的 run 的东西上去。下载用的路径校验（FR-015）拒绝路径跳转，清理器与校验用的是同一类约束。

**「以内」按解析后的真实路径判定，不按字面路径判定**。字面上在 run 目录里，也可能指向外面：
run 目录里的一个**目录链接（junction / 符号链接）**指向别处时，`lnk/state.json` 字面上在 run
目录里，解析后却是链接所指目录的状态文件。因此每一条目都**解析真实路径**（沿途的链接全部跟随）
再判定是否在 run 目录内；解析后越界的条目**被拒绝并记入 `rejected[]`**，校验与清理都不跟随。
锚点是「按 run id 得到的 run 目录」本身：run 目录的上级可以是链接（数据目录本身是链接是常事，
此时普通文件仍算在目录内），但 run 目录**自己**若是链接，则它里面的文件全部解析到目录之外，
于是它的清单条目全部被拒。**文件已经不在了**（被清理过或缺失）时，按它**最深的存在祖先**
解析：这种条目仍然是「缺失」，不是「越界」——否则清理过的 run 会突然被当成清单越界的 run。
`results/` 本身是目录链接时，清理器**只摘掉链接**，不删除链接所指的树。

**清理记录只增不减**。清理器在 run 目录里留下 `evidence-cleaned.json`，记下删了哪些文件。
第二次清理若又删了别的文件，新记录与旧记录**合并**而不是覆盖：删除的事实一旦记录就不会被撤回。
否则第二次清理会把第一次删掉的文件的解释抹掉，那些文件会被重新报成 `missing`——而 `missing`
与真实篡改是同一个信号，篡改告警就失去意义。

**清理是离线操作**。Bridge 运行时会持有数据目录的锁，并把内存里的状态写回 `state.json`；
此时清理会删掉正在产出证据的 run 的目录，而 Bridge 下一次保存就会把指向已删文件的状态写回去。
因此清理器先查锁，锁被持有时**拒绝**（退出码 3），与 `tools/migrate_state.mjs` 的同一规则。

**清理同时删掉 store 里的副本**。证据可能含 PII，清理若把字节留在 store 里，那不叫删除——
数据还在盘上，只是不在 run 目录里。因此 `clean` 这条命令**总是**顺带回收无引用的 blob，
并把回收的份数与字节数记进输出。`--dry-run` 则**什么都不删**，store 也不例外。

每一次清理写一条**日志**（`<data-dir>/evidence-retention-journal.jsonl`，仅追加）：删了什么、
留下了什么、是哪一次 run。证据可能含 PII，`docs/06-DATA-DESIGN.md` §4 要求的「可审计删除」
由这份日志承担。日志只记**实际删掉**的文件——`rm` 对已不存在的文件不报错，所以「删掉了」
必须由调用方自己核对，否则日志会说删了其实没删。

## 4. 保留期怎么算

- 只有**终态**的 run 才有资格被清理：`passed` / `failed` / `cancelled` / `error` /
  `interrupted`。`queued` / `running` / `cancelling` 的 run 还在产出证据，不是待清理的对象。
- 年龄从 run 的 `finishedAt` 起算（证据完整的那一刻），没有 `finishedAt` 时退回 `createdAt`。
- 默认保留期 **30 天**。默认值刻意宽松：一次没人看过的失败的证据被意外删掉，代价比多占
  几天磁盘大得多。需要更短的周期由调用方显式给出。

## 5. 接口面

| 接口 | 作用 |
|---|---|
| `GET /api/runs/:id/evidence` | 校验该 run 的证据：`verified` / `missing[]` / `changed[]` / `extra[]` / `rejected[]` / `cleaned[]` / `truncated` |
| `GET /api/runs/:id/manifest` | 读回该 run 的清单原文 |
| `GET /api/evidence/retention?days=N` | 保留期**计划**：哪些 run 到期、证据占多少空间、多少字节被多份共享 |
| `GET /api/evidence/dedup` | 去重报告：哪些内容存了多份、共享多少字节 |

`GET` 接口**只读**：不写、不修复、不删除。清理是**离线**命令：

```bash
node tools/evidence_retention.mjs plan    --data-dir <dir> [--days N]   # 看会发生什么
node tools/evidence_retention.mjs clean   --data-dir <dir> --days N --yes # 真的清理
node tools/evidence_retention.mjs verify  --data-dir <dir>              # 逐个 run 校验
node tools/evidence_retention.mjs journal --data-dir <dir>              # 读清理日志
```

`clean` 不带 `--yes` 会拒绝执行（退出码 2）：清理不会因为一次手滑就发生。
`clean` **总是**顺带回收 store 里无引用的 blob（证据可能含 PII，清理不能只删一半），
`--dry-run` 则什么都不删。`--prune-store` 仍然接受，但已无独立作用。

`verify` 的退出码：0 表示全部相符或已被保留期清理；1 表示有 run 的证据被**改动**、
或**在没有清理记录的情况下**丢失、或清单越界指到 run 目录之外（含经由目录链接越界）。

## 6. 已知边界（写明，不含糊）

- **清单未签名**：能写数据目录的攻击者可以同时改文件和清单，因此**不得**宣称 WORM 存储或
  防篡改等级。本项检测的是「文件不再与归档时的清单相符」，这正是 `docs/06-DATA-DESIGN.md`
  §4 要求的性质。
- **被保留期清理掉的证据报为「已清理」，不是报为「不一致」**：清理器在 run 目录里留下
  `evidence-cleaned.json`（删了哪些文件、何时删的），校验据此把缺失的文件算作「已按保留期
  清理」，**不判失败**。没有这条记录的话，每一次清理都会让 `verify` 永久退出 1——与真实篡改
  是同一个信号，篡改告警也就失去意义。没有清理记录而丢失的文件，仍然照旧报 `missing` 并判失败。
- **`extra` 文件不使校验失败**：归档后被**追加**的文件不会让已归档的文件失效，但答案会把它
  列出来，因为文件夹已不是清单描述的那一份了。
- **清单越界的条目被拒绝**：`rejected[]` 里的条目指向 run 目录之外，校验与清理都**不跟随**，
  并把它报出来。这样的 run 判为不可校验。越界的判定按**解析后的真实路径**做：字面上在 run
  目录里、但经由目录链接（junction / 符号链接）指向外面的条目，同样被拒绝——**链接与 junction
  一律不跟随**。文件已不存在时按最深的存在祖先解析，它仍然是「缺失」而不是「越界」。
- **清理记录只增不减**：`evidence-cleaned.json` 里的删除记录只会被**追加**，不会被覆盖。
  第二次清理删除别的文件时，第一次清理的记录仍然在，那些文件因此仍然被报为「已按保留期清理」，
  而不是重新变成 `missing`。
- **截断的豁免很窄**：只有当文件夹里再没有清单未列出的证据文件时，被截断的清单才被豁免；
  一条清理记录本身不能豁免它。清理器移除「清单未列出的文件」时不受条目上限约束。
- **400 个文件的上限是产品决定**：大套件开启 trace 时，Playwright 的 HTML 报告加上
  `results/` 很容易超过 400。这类 run 在清理前一直「未通过校验」，因为清单确实没有覆盖全部
  证据。上限目前是写死的常量，需要时可调高。
- **摘要不归一化**：因此同一份内容在不同平台（CRLF 与 LF）会得到不同摘要，也就不会被去重。
  这是刻意的——归一化会削弱内容敏感性。
- **单机存储**：store 在数据目录内，跨数据目录不共享；没有远程证据后端（属 ATS-509）。
- **清理不做可逆恢复**：被清理的证据不再可恢复（store 里的副本也会一并回收）。
- **一次就地改写会影响共享该内容的其他 run**：硬链接的各副本共享 inode，所以改写一个 run 的
  证据文件会同时改掉其他共享该内容的 run，那些 run 会被报为 `changed`。这是**如实**报出，
  不是误报，但说明 store 的副本**不是独立备份**。
- **清理器只查锁、不持锁**：查完锁之后、Bridge 启动之前仍有一个竞争窗口。这是与迁移工具的
  已知差别（迁移是持锁执行的）。

证据见 `docs/evidence/ATS-209/`。用例：`tests/evidence.test.mjs`（UT）、
`tests/evidence-it.test.mjs`（IT）与 `tests/evidence-cli.test.mjs`（CLI）。探针：
`tools/ats209-probes/`。
